# Hostinger deployment for Easy Zay Mm

The Hostinger deployment uses the repository's `backend/` directory as the application root. The production release now includes the tested Composer `vendor/` directory and Vite `public/build/` output, so Hostinger does not need to run Composer, npm, or a custom Build command.

## Current Hostinger settings

In hPanel → **Websites → Manage → Advanced → Git**:

- Repository: `hidecard/marketplace-app`
- Branch: `main`
- Root directory: `backend`
- Build command: `bash scripts/hostinger-build.sh`
- Auto-deployment: enabled

The screenshot confirms that Hostinger deploys `backend/` directly into `public_html` because `public_html` contains `bootstrap/`, `config/`, `database/`, `public/`, `routes/`, and `scripts/`.

Set the domain document root to:

```text
.../public_html/public
```

Keep the production environment file outside the Git deployment directory:

```text
/home/<account>/domains/easyzaymm.com/.env
```

The Laravel bootstrap is configured to load this external `.env`. Never commit it or put it inside `public/`.

Create the storage link once, if it does not already exist:

```bash
cd .../public_html
php artisan storage:link
php artisan migrate --force
php artisan optimize
```

## Why Composer is no longer needed after each push

`backend/vendor/` is now tracked in Git and was copied from a successful GitHub Actions production build. `backend/public/build/` is also tracked. Therefore every Hostinger Git sync receives:

```text
public_html/vendor/
public_html/public/build/
```

A normal code push does not need a server-side Composer install. Composer is only needed when `backend/composer.lock` changes; in that case regenerate the tracked vendor directory in CI and commit the updated release.

The optional `scripts/hostinger-build.sh` first checks for the tracked `vendor/autoload.php`. If it exists, it does not run Composer. It only has a fallback persistent cache for older deployments where vendor was already missing.

Before it checks Composer or runs the frontend build, `hostinger-build.sh` now runs
`scripts/hostinger-backup.sh`. The backup is written outside `public_html` and
contains a compressed MySQL dump, a compressed `storage/app/public` archive, and
SHA-256 checksums. If the database dump, uploaded-storage archive, or required
backup tools fail, the deployment stops instead of continuing with an unprotected
release. Set `BACKUP_BEFORE_DEPLOY=false` only for a deliberate non-production
maintenance run.

## Uploaded files and vector folder

Runtime uploads must stay outside the tracked release:

```text
public_html/storage/app/public/
```

The `public/storage` symlink should point to `../storage/app/public`. The Git release does not contain or delete uploaded media. Restore previously deleted vector files from a Hostinger backup into:

```text
public_html/storage/app/public/vector/
```

The backup directory is outside the release tree by default:

```text
/home/<account>/.easyzaymm-backups/<UTC-timestamp>/
```

It retains 30 days by default (`BACKUP_RETENTION_DAYS`). Backups are intentionally
not stored inside GitHub artifacts or the application directory.

To perform a manual restore, first put the site in maintenance mode and verify the
backup manifest, then run the explicit confirmation command:

```bash
cd .../public_html
CONFIRM_RESTORE=YES bash scripts/hostinger-restore.sh 20261014T021500Z
php artisan optimize:clear
```

The restore script refuses to run without `CONFIRM_RESTORE=YES`, validates both
archive checksums, restores MySQL, and replaces `storage/app/public` from the
selected backup. Reopen traffic only after checking login, product images,
checkout, and admin flows.

## GitHub Actions

`.github/workflows/hostinger.yml` validates the release on every push with Laravel tests and the frontend build. The tested production artifact generated by CI is committed to the repository so Hostinger's Git integration can deploy it without a server build step.

`.github/workflows/hostinger-backup.yml` provides a daily 02:15 UTC SSH backup
and a manual workflow dispatch. Configure these repository secrets before using
it:

| Secret | Purpose |
|---|---|
| `HOSTINGER_SSH_HOST` | Hostinger SSH hostname |
| `HOSTINGER_SSH_PORT` | SSH port, normally `22` |
| `HOSTINGER_SSH_USER` | SSH deployment/backup user |
| `HOSTINGER_APP_ROOT` | Absolute deployed root, such as `.../public_html` |
| `HOSTINGER_SSH_KEY` | Dedicated private key |
| `HOSTINGER_SSH_KNOWN_HOSTS` | Pinned `known_hosts` entry |

The workflow is an additional daily backup. The pre-deploy backup from
`hostinger-build.sh` remains the safety barrier for every release. If the
Hostinger Git integration does not execute a build command, configure Hostinger's
cron panel to run this at least once daily and before a planned deployment:

```cron
15 2 * * * cd /home/<account>/public_html && BACKUP_BEFORE_DEPLOY=false bash scripts/hostinger-backup.sh >> /home/<account>/.easyzaymm-backup.log 2>&1
```
